# 独立分析

> 分析基线：`agent-CI-Infra/bot` `main@95231e8`（2026-11-12）。方法：通读官方 `docs/`，抽查源码入口、安全原语、数据库迁移、任务引擎、RoleRun、manager 与 runner，并在本机部署验证。**不是**逐行代码审计，也不是渗透测试。

## 1. 它解决了什么问题

大多数“AI 改代码”的产品停在“给一个 Agent 一个仓库，让它开 PR”。LaunchPad 多做了三件事：

1. **把权限收进控制面**：仓库容器不持有 GitHub 写凭据和模型 Key；模型需要读 GitHub 时兑换短时只读令牌。
2. **把“跑完”与“验收”分开**：执行器正常结束不算通过；候选要经独立 QA、契约、发布前置和 GitHub 写入校验。
3. **把流程做成可审计的状态机**：事件先落库、任务有 claim、每次执行有 lease epoch、每个动作有记录。

这让它更像一个**部门级的工程流水线**，而不是一个聊天机器人。

## 2. 设计上真正值得肯定的地方

### 2.1 单一入口 + 单一事实源

- 一个 HTTP 监听承载控制台、登录、回调和 Webhook（`src/main.ts:67-69`）；没有第二个管理端口。
- SQLite + 先落库再确认；`deliveries` / `processed_deliveries` / `dispatch_events` 形成幂等链。
- 费用、任务、看板、审计都从同一份数据库投影，不各自维护一套。

### 2.2 凭据分层

- `SecretBox`：AES-256-GCM + AAD 绑定记录（`src/core/security.ts:47-61`）。这条设计比“把 key 加密存起来”强，因为它阻止密文在记录之间搬运。
- 主密钥、manager token、运行令牌、只读令牌、用户 OAuth token 各有生命周期与暴露面。
- 运行令牌只存哈希，绑定 epoch 和能力；旧 epoch 立即失效。

### 2.3 围栏（fencing）而不是“相信”

- 任务 claim token 写入 SQL 围栏；旧执行不能覆盖新状态（`src/agent/engine.ts:189-214`）。
- RoleRun 的 lease epoch 让“重启/接管”可证明；事件序号回退、跳号、重复、迟到都拒绝。
- 发布前固定一次工作树快照；测试在快照之后运行，测试生成物不进入 PR。

### 2.4 自动化模块是纯函数

`src/automation/` 的标签、门禁、合并队列模块不访问网络、不写数据库，只输出动作。规则可以用固定事件回放测试。这是“可测试的运维策略”的正确形状，很多同类系统把规则写进 YAML + 脚本，最后无法回放。

### 2.5 诚实的失败分类

失败不是一句“出错了”，而是外部波动 / GitHub 权限 / GitHub 拒绝 / 模型 / 项目电脑 / 仓库内容 / 条件变化 / 写入未知 / Bot 自身。它决定重试、停点和给人看的下一步。这比“自动重试三次”更接近可运维。

### 2.6 文档密度

上游 `docs/` 覆盖接入、规则、部署、身份、RoleRun、Harness、门禁、发版、外部执行端、管理对话、飞书。对这么大的系统，这是稀缺优点。

## 3. 边界与弱点

### 3.1 它仍然信任宿主

manager 挂载 `/var/run/docker.sock`。**攻破 manager 等于宿主 root。** 容器隔离、只读根文件系统、非 root 用户都很重要，但它们不能改变这个事实。对单人/单团队自托管是合理取舍；对多租户 SaaS 不够。

### 3.2 模型仍是最大的不确定性

系统能把“不可信输出”关进 `create_pull_request` 和 QA，但不能保证模型不做出错误的、但语法合法的修改。提示注入、过度拟合测试、错误抽象都还在。上游用“固定提交 + 快照 + 契约 + 独立 QA”降低概率，不是消除。

### 3.3 单机 SQLite

WAL + FULL 适合单控制面。它没有分布式锁、没有只读副本、没有在线迁移保障。项目一多、事件一密，写放大和 WAL 增长会成为运维问题。这不是缺陷，是选型边界。

### 3.4 复杂度集中在 `src/agent/engine.ts`

约 965 行，承担任务状态、模型循环、工具、GitHub 发布、恢复。它是系统的心脏，也是最难改的文件。建议后续把发布、恢复、工具网关进一步拆开，降低单文件认知负担。

### 3.5 供应链与镜像

默认 `latest` 方便，但生产应固定 digest/版本。文档没有强调镜像签名验证；执行器（Pi、Claude Code、ACP、Codex）也需要固定版本与校验和。

### 3.6 运维门槛

它要求：Docker、一个公网 HTTPS 入口、GitHub App 创建权限、模型 Key、Tunnel/反代。第一次接入的七步向导已经很好，但仍不是“点一下就能用”。对非工程团队，门槛偏高。

## 4. 成熟度评分（主观，按证据）

| 维度 | 分数 | 理由 |
| --- | --- | --- |
| 架构清晰度 | 8/10 | 平面分离、单一入口、状态机明确；`engine.ts` 偏大 |
| 安全设计 | 7/10 | 凭据分层、AAD、令牌、围栏；Docker socket 是硬边界 |
| 可测试性 | 8/10 | 纯函数自动化、离线测试、假 GitHub/假模型、Playwright |
| 可运维性 | 7/10 | 健康检查、失败分类、日志、备份；单机 SQLite |
| 文档 | 9/10 | 覆盖广、更新勤；部分页面很长 |
| 可扩展性 | 6/10 | 单控制面、单机；多实例需手工隔离 |
| 上手成本 | 6/10 | 七步向导 + 基础设施要求 |
| 产品完成度 | 7/10 | 检视/开发/发版/门禁齐全；UI 与边界仍在演进 |

**综合：7.3/10。** 它是一个认真、可运行、可审计的单团队工程 Bot；不是开箱即用的多租户平台。

## 5. 与 FlyBot / Fledge 的定位对比

| | LaunchPad（本项目） | FlyBot | Fledge |
| --- | --- | --- | --- |
| 核心 | 部门公共 GitHub App + 控制面 | 由多个长期 Bot 组成的团队，跑在 DSH 上 | 托管“会自己长大的仓库” |
| 工作单位 | Issue/PR 事件 → 任务 → 角色运行 | Bot 会话、群聊、任务 | Job → 可审查 PR |
| 权限模型 | GitHub App installation + 派生人类授权 | 人类 owner、Main Bot、树 | GitHub 登录 + 仓库接入 |
| 执行隔离 | 每仓库虚拟电脑 + 每次运行容器 | DSH Session/工具 | 容器 Job |
| 最强处 | 工程流水线、审计、门禁 | 多 Bot 协作与长期记忆 | 自助接入、按任务 PR |
| 最大风险 | Docker socket / 模型 | 多 Bot 权限与上下文串扰 | 托管多租户隔离 |

三者不是替代关系：LaunchPad 更像“组织级 CI/Bot 控制面”，FlyBot 更像“Bot 团队运行时”，Fledge 更像“托管式自我迭代服务”。

## 6. 建议（按优先级）

### P0（采用前必须做）

1. **固定镜像与执行器版本**：`BOT_IMAGE_TAG`、Pi/Claude/ACP 版本、校验和；升级前审阅 diff。
2. **把 manager 当 T0 资产**：独立主机或至少独立 Docker daemon；限制谁能访问宿主；审计所有容器操作。
3. **备份演练**：四个卷一起备份，并实际恢复一次；只备份数据库而丢 `bot-keys` 等于没备份。
4. **出站 allowlist**：模型 URL 与外部转发限制私网/重定向；防止 SSRF。

### P1（采用后尽快）

5. **给 `engine.ts` 拆模块**：发布、恢复、工具网关分开，补状态机不变量测试。
6. **提示注入红队**：把“仓库内容诱导模型执行命令/泄露上下文”的用例纳入 CI。
7. **WAL 与写放大监控**：任务量上来前先观测；必要时把读投影拆出去。
8. **审计保留策略**：明确保留期、导出和不可篡改存储。

### P2（产品化）

9. **多实例部署模板**：健康检查、Tunnel、资源限额、升级脚本一次配好。
10. **公共看板的发布前预览**：默认关闭 + 明确 consent UI。
11. **更细的按仓库预算**：模型/CI/容器成本上限。
12. **可视化的“为什么没开发”**：把 Manager 的 `ignore` 理由做成可筛选的指标。

## 7. 开放问题

- 一个控制面准备服务多少个组织/仓库？超过多少任务/天时 SQLite 需要换？
- 是否允许项目管理员自带模型 URL？如果允许，SSRF 边界怎么定？
- 外部执行端是否需要独立的信任等级（例如只读检视 vs 可写开发）？
- 公共看板是否会成为“默认公开”的隐私风险？
- 发版自动化是否应该允许“预发布自动发布”，还是永远保留人工点击？

## 8. 结论

LaunchPad 的价值不在“让模型写代码”，而在**把模型写代码这件事变成可审计、可回滚、可拒绝的工程流程**。它的设计选择（单一入口、凭据分层、先落库、围栏、纯函数自动化、诚实失败分类）是成熟的；它的代价是运维门槛和 Docker socket 这个硬边界。

**如果你是一个工程团队，愿意维护一台 Docker 宿主和一套 GitHub App，它值得采用。如果你要的是多租户 SaaS 或零运维，它还不是那个产品。**
